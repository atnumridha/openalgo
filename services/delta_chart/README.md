# Manual Delta India chart API

This integration is independent of the selected OpenAlgo broker and the Delta scalper. It never arms or configures a bot. All execution is an explicit authenticated, CSRF-protected action against `https://api.india.delta.exchange`.

## Maker entries, market risk exits

Entries and take-profit orders use `limit_order`, `post_only: true` and `time_in_force: gtc`. Explicit Close, chart × close and managed directional exits use the exact fresh opposite-side quantity with `order_type: market_order` and `reduce_only: true`, without a limit price, post-only flag or forced GTC. Stop-loss orders use `market_order`, `stop_loss_order`, a reviewed `stop_price`, `stop_trigger_method: mark_price` and strict reduce-only. They have no limit price, post-only flag or forced GTC. Market execution can slip, and order acceptance does not guarantee a fill or a maximum loss.

- Entry requires an explicit positive tick-aligned reviewed limit price. Market entries remain rejected. Attached bracket exits remain unsupported; the worker creates separate reviewed exits after verified fills.
- Close requires `position_version`, plus matching reviewed side/size if supplied; no quote or reviewed price is required. A remaining owned entry must be cancelled before closing so it cannot add exposure afterward.
- Protect accepts exactly one SL or target per request. SL is a mark-triggered market stop, target is a maker stop-limit with equal trigger/limit levels. Both are opposite-side, exact-position-size and reduce-only. They are independent orders, not atomic OCO.
- Edit requires the exact live order version. A reduce-only mark-triggered market SL can edit its stop trigger/size without a limit price, post-only field, immutable order type or GTC. Existing entry/target limit edits retain post-only and require known GTC. Existing maker SLs retain their type through PUT; managed migration replaces them safely instead of trying to edit an immutable order type.
- Cancel addresses only the selected exact order. Unknown mutation outcomes remain pending and are never blindly retried or silently repriced.

This follows the [official CreateOrderRequest and EditOrderRequest schemas](https://docs.delta.exchange/), including `market_order`, `stop_loss_order`, mark triggers and reduce-only. No financial mutations are performed during development verification.

## Endpoints and credentials

- `GET /delta-chart/api/state?symbol=BTCUSD` refreshes owner-scoped positions, open orders, leverage and public quotes. Independent reads run concurrently. Fills cover the last 24 hours and are cached for ten seconds. `asof` is the request-start timestamp. `ticker.bid` and `ticker.ask` are positive finite public `quotes.best_bid`/`best_ask`, or null if unavailable. Orders include `post_only: true` for a limit order when the broker explicitly reports boolean true, or when the exact confirmed server request and unchanged broker timestamps prove our own maker-only acknowledgment. An explicit false flag always wins; foreign/missing evidence stays false. Position `version` binds stable product, quantity and entry information; order `version` binds the raw broker record. `pending` and the last twenty `receipts` preserve durable action outcomes.
- `POST /delta-chart/api/connection` accepts `api_key` and `api_secret` (legacy `key`/`secret` aliases also work). The candidate is verified with read-only `GET /v2/users/trading_preferences` before the previous connection can be replaced. Credentials use OpenAlgo's existing auth encryption and are stored per app username in `db/delta_chart.db`; they never appear in responses or replace Kotak credentials.
- The existing private Delta MCP connection is reusable only by `DELTA_CHART_OWNER`, or when the current username is the sole configured OpenAlgo username. Its file must be owned by the server user, a regular file with no group/other access, and configured for India production. The reader never rewrites that file or copies credentials into controller configuration.
- `POST /delta-chart/api/action` requires a canonical UUID `request_id`, `symbol`, opaque `account` from fresh state, and `action`. Entry leverage defaults to 5, capped at 200 and the product margin ceiling. Close/protect require `position_version`; edit/cancel require `order_id` and its `version`.

A UUID is durably bound to the complete payload. SQLite serializes unresolved actions per actual API key and product across workers. Mutating requests are never retried. Ambiguous transport outcomes remain pending and block new product actions. GET state reconciles only from read-only evidence: exact client ID for entries/closes/single protective legs, identified order status/fields for cancel/edit, or the acknowledged leverage value for an interrupted leverage-only stage. Maker edits additionally require observed broker post-only status before reconciliation can confirm them. Legacy pre-policy bracket intents retain conservative read-only reconciliation. A leverage-only reconciliation explicitly reports that no entry was submitted. Missing or contradictory evidence stays pending; never clear the ledger or blindly resubmit to recover. A crash before sufficient evidence may require manual broker reconciliation.

The API rereads ticker and real-time position immediately before a mutation and fails closed if those reads exceed five seconds or the position changes. Protection prices must match ticks and be on the correct side of the mark. Changing leverage requires an immediate fresh flat-position/no-open-orders preflight; external clients can still race broker requests. Protective edits retain the opposite side and cannot exceed the current position quantity. Gross unrealized P&L is read from the broker or calculated for explicitly vanilla contracts; unknown values remain null.

Run `.venv/bin/python -m unittest discover -s test -p 'test_delta_chart*.py'` for mocked backend and Flask route verification.

## Available-balance percentage sizing

State optionally includes `sizing: {available_balance, currency, maker_fee_rate, taker_fee_rate, fee_tax_rate, version}`. Supported sizing requires a live vanilla perpetual settled in USD and exactly one wallet row whose asset ID and symbol match the product's USD settling asset. Only that row's explicit `available_balance` is used. Total `balance`, INR display values, INR wallets, referral assets and fee credits are excluded. Missing or unsupported balance/fee metadata yields `sizing: null`; manual quantity entry remains available. Zero available balance is reported as zero and cannot fund a positive percentage entry.

The supported balance fractions are `0.10`, `0.25`, `0.50`, `0.75` and `1`. Default leverage remains 5×. With `P = max(reviewed limit price, current mark, valid positive current bid, valid positive current ask)` and contract value `CV`, the conservative whole-contract estimate is:

`floor(fraction × available_balance × 0.99 / (P × CV × (1/leverage + maker_fee_rate × (1 + fee_tax_rate))))`

The 1% buffer applies to the selected allocation. The API product's `maker_commission_rate` is a fractional rate: `0.0002` is 0.02%. The [official Delta India fees page](https://www.delta.exchange/fees?tab=trading-fees), checked on 1 November 2026, states that 18% GST applies to trading fees, so `fee_tax_rate` is `0.18`. The estimate includes opening maker fees plus GST and margin; it is not a guarantee of broker acceptance, future fees or liquidation safety. Broker notional limits, scaled margin and order validation remain authoritative.

A percentage entry sends `balance_fraction` and the reviewed state's `sizing_version`, alongside its explicitly reviewed `size`, `price` and leverage. The version binds the account, product, USD available balance, maker fee, GST, contract value, initial margin and buffer. Any changed balance, including an increase, or changed fee/margin metadata requires another review. The server never increases or silently changes the reviewed contract quantity.

Before changing leverage and immediately before submitting the entry, concurrent read-only preflight refreshes wallet balances, public product/fee metadata and ticker quotes alongside the existing position/order checks. Reads exceeding five seconds, unavailable sizing, a changed version, zero affordable contracts, or a reviewed quantity above the fresh fee-inclusive budget reject the entry before the corresponding mutation. Existing idempotency and unknown-outcome handling remain in force. In particular, if leverage was already acknowledged and a later preflight fails, the durable intent conservatively records that stage and does not blindly retry an entry. All new entry requests retain strict post-only limits; reduce-only risk exits follow the market policy above.

## Live balances and open-position P&L

`state.accounting` exposes `{currency, balance, available_balance, position_gross_pnl, position_entry_fees, estimated_maker_exit_fee, estimated_exit_fee, exit_fee_basis, position_net_after_fees, fee_status, message}`. All monetary values use the matched USD settling asset. Wallet `balance` and explicit `available_balance` are independent of percentage-sizing support and are passed through from Delta without deducting historical commissions a second time. INR display values and other asset wallets are excluded.

The open-position gross P&L is separate from trading costs. Estimated market closing cost is `abs(position.size) × contract_value × current_mark × taker_commission_rate × 1.18`; the actual fill price and resulting exit fee remain unknown. Net-after-fees is therefore an estimate, and is available only when entry costs are proven: `gross − verified_entry_cost − estimated_closing_cost`. It excludes funding and realized trade results. This is not account-wide net P&L or wallet equity.

Actual entry costs require successful complete pagination of the selected product's 24-hour fill window and a simple, unreduced flat-to-current lifecycle. The latest broker fill snapshot must match the current size and entry, each entry must link through `new_position.size` and `last_fill_uuid`, weighted entry prices must reconcile, and the summed costs must reconcile to the latest `new_position.total_commission_paid`. Partial closes, reversals, missing older entry fills, ambiguous ordering or missing metadata leave entry fees and net null rather than guessing an allocation. Open positions force fresh paginated fill reads instead of reusing the ten-second history cache. A history failure leaves balances and gross P&L available with fees/net unverified.

Each actual fee uses `meta_data.total_commission_in_settling_asset` once, reconciled to the cash commission and trading-fee credit consumption. It is not multiplied by GST again. GST provenance additionally requires the live India payload's explicit `rack_commision` versus `rack_commission_without_gst` reconciliation at 18%; promotional totals are not reconstructed from the public fee rate. Missing evidence stays unknown. Legitimate proven waived fees or maker rebates retain their reported zero or signed values.

The official [Fill and FillMetaData schemas](https://docs.delta.exchange/#fill) document commission, fee-credit totals, snapshots immediately after each fill and the lifecycle fields. The extra explicit pre-GST rack field was verified in the India GET-only live payload on 1 November 2026; code deliberately treats older payloads lacking that evidence as incomplete.

`fee_status` is `verified`, `incomplete`, `flat` or `unavailable`, with a short explanation. A flat position has zero **current-open-position** P&L/cost metrics and a message that these zeros do not describe historical trading fees. Unknown costs on an open position remain null. This accounting extension makes no exchange mutations and also works for metadata-supported USD vanilla perpetuals such as XAUTUSD.

## Reviewed managed-entry plans

Every chart API entry must include `auto_protection: {stop, target, source_time, interval_seconds, reason}`. Levels are reviewed by the user and calculated outside the backend; the server does not choose trends or invent levels. The plan is persisted before any entry/leverage mutation, bound to the app user, account, product, selected symbol, parent request UUID and reviewed entry. Managed entry requires a flat selected product with no existing orders. Source time is the closed candle's UTC start timestamp; interval is immutable. Initial stop and target must match ticks and sit beyond the entry/current mark on their correct sides. Unsupported attached broker brackets remain prohibited.

State includes `managed_plans: [{id,status,message,side,entry_order_id,stop,initial_stop,target,source_time,interval_seconds,entry_price}]`. `initial_stop` remains immutable; `stop` can tighten, and `entry_price` becomes the proven actual entry after proven fills. GET only reads and reconciles evidence; it never advances a financial action.

Authenticated CSRF-protected `POST /delta-chart/api/manage` accepts `{plan_id, decision: 'sync'|'cancel_entry'|'trail'|'exit', source_time, stop?}`. Account, product, symbol and owner come from the stored plan. There is no browser-generated child UUID: each child operation receives a deterministic durable request ID and immutable payload through the existing intent ledger. The source must be at least the original reviewed candle, already closed in the plan's interval, and no older than two intervals plus ten seconds after close. Responses are `{status:'confirmed'|'pending'|'rejected', message, plan_id, plan_status, order_id?}`.

Each POST makes at most one child financial mutation. Sync proves the exact filled parent quantity/side, actual entry and complete flat-to-current fill chain entirely attributable to that parent order, including broker `last_fill_uuid` snapshots. A verified **partial fill receives its market SL immediately**. If further parent fills increase exposure, the next sync first resizes only that owned SL to the fresh exact quantity while retaining the current broker stop price. Once that stop quantity matches, a separate sync cancels the remaining owned entry; a later sync places the target for the retained filled position. Foreign or ambiguous exposure is never managed. Actual GST/commission availability does not block initial protection or an owned exit: ownership is proved independently from fee accounting. Fee-aware trailing requires verified fee evidence.

All account/product actions and complete management decisions share a process-safe reentrant file lock across server workers. This includes manual close, so a stale management decision cannot place another leg or overwrite its closing state after that close. Lock files contain no credentials; the OS releases locks if a process dies. SQLite independently binds operation UUIDs and unknown outcomes. A rejected stored child response is never treated as confirmation or used to update the reviewed stop.

After ownership proof, sync places one reduce-only market stop, then the maker target in a later POST. The exact owned mark-triggered market SL and post-only limit target must both be observed before status becomes active. Market stops can slip; maker targets can remain unfilled. Trail can only tighten the existing owned broker stop and cannot loosen a manually tightened stop. A profitable stop may cross the position entry, provided it remains on the proper side of the fresh mark and inside any known liquidation price. Targets stay beyond the entry. Known liquidation violations block placement clearly; unknown liquidation does not create a safety guarantee at high leverage.

Cancel-entry applies only to the exact owned parent remainder, including a partially filled parent. Proven partial exposure receives/resizes its SL before that remainder cancellation. Explicit manual close rejects with “Cancel remainder first” while the owned parent can still add exposure. Exit creates a single owned reduce-only market close for the fresh exact position, without using a quote as a limit price. A resting or uncertain close is never duplicated. Explicit manual close durably pauses matching plan management before broker submission and records its request as an owned exit; a definitely rejected manual close permits previously reviewed fixed protection to continue, without retrying that close. Unknown close outcomes keep management paused until reconciliation. When the position is flat, subsequent sync calls cancel only acknowledged owned sibling exit orders, one per POST, then finish the plan. The production blueprint service factory starts a daemon that progresses **only previously reviewed fixed protective plans**: initial SL, partial SL resizing, remainder cancellation, target and flat cleanup. It runs a bounded round of up to 100 active plans, then waits two seconds. Each plan shares the durable cross-worker lock and existing intent ledger. This worker never creates entries, chooses levels, trails or makes directional exits. It may use the original reviewed fixed levels without current chart-candle evidence; public management requests retain the fresh closed-candle requirement. The TradingService constructor does not start a worker, and tests invoke one mocked tick explicitly. Broker-held protection persists when the chart closes; trend-based trailing and directional decisions require the chart driver.

Statuses: `awaiting_entry`, `partial_fill`, `placing_protection`, `active`, `closing`, `cleanup`, `pending`, `blocked`, `completed`, `cancelled`, `rejected`. Blocked/completed/cancelled/rejected plans do not automatically advance. Pending sync performs read-only reconciliation before another child can proceed. Missing broker evidence, unknown mutation outcomes and ownership changes never justify a blind retry or foreign order cancellation.

The full mocked lifecycle test exercises entry ACK → full fill → SL → target → tighter stop → explicit/opposite-trend market exit → flat → owned sibling cleanup. No real financial mutation is performed by tests. Gross P&L for supported USD vanilla contracts is always recomputed from real-time `(mark-entry) × signed_size × contract_value`, avoiding a lagging margined snapshot after reversals.

Explicit acknowledged edits of owned SL/target orders update the visible managed levels; the original `initial_stop` remains immutable. Automatic trailing also compares against the current broker stop so it cannot loosen a manual tightening. Market stop placement and resizing are best efforts after fill observation; network delays, rejected conditions, missing ownership evidence, liquidation and market slippage mean neither immediate protection nor execution/maximal loss is guaranteed. Unknown outcomes are not retried with new identifiers.


## Explicit existing-position adoption

`POST /delta-chart/api/action` additionally supports `action: adopt` with the usual canonical `request_id`, `symbol`, `account`, exact `position_version`, reviewed `auto_protection`, and nullable `existing_stop: {id,version}` / `existing_target: {id,version}`. This action only registers a durable plan after fresh read-only broker checks; it does not submit an entry or any other exchange mutation. The confirmed response includes `plan_id`. Every present protective leg must be explicitly identified and match its reviewed version. Multiple same-kind legs, unrelated live orders, a non-reduce-only leg, wrong side or a quantity different from the full current position require manual review. The chosen stop cannot loosen the existing stop and must remain on the valid side of current mark; a profitable stop beyond entry is allowed.

The adopted plan is bound to the exact size/entry position version and the latest position-affecting fill UUID/snapshot from a complete successfully read fill window. Missing or ambiguous ownership evidence rejects adoption; no commission/GST evidence is required for this ownership check. The fill marker is rechecked during management and immediately before a managed order mutation, so an identical-size/entry close and reopen does not inherit the old authorization. Subsequent changes pause management rather than assuming ownership of a replacement position. The worker creates a full-size market SL while the reviewed old SL remains. Only after observing the owned replacement as an acknowledged reduce-only mark-triggered market stop for the full position can a later sync cancel that exact unchanged reviewed old SL. Target replacement follows the same sequence. A timeout, rejected replacement, invalid replacement type/trigger/quantity or changed legacy order leaves old protection untouched. These transient duplicate exits remain reduce-only. Explicitly reviewed legacy siblings are also cleaned up if the adopted position becomes flat. Adoption never silently imports another position or authorizes new entries.

Liquidation and non-vanilla risk/P&L fields from the slower margined endpoint are used only when both signed size and entry numerically match the real-time position. Stale opposite-direction or prior-entry rows produce unknown liquidation, not an incorrect stop boundary. Live mark-side checks remain required.


## Maker acknowledgment provenance and placement time

Delta's documented Order response schema and the live India GET response omit the request's `post_only` field. Absence therefore does not establish a maker flag for arbitrary orders. For this application's orders only, maker verification may use the durable **confirmed** POST/PUT request containing strict `post_only: true`, exact broker order ID (and client UUID for creation), product, side, quantity, prices, conditional fields, reduce-only and GTC limit type. The observed `updated_at` must equal the ACK's persisted broker timestamp. Previously acknowledged creates lacking stored ACK metadata qualify only while nonempty `created_at == updated_at`, proving no subsequent edit. Changed economic fields, changed timestamps, an explicit false flag, non-limit order, or an unrelated/unknown order fails this check. Future create/edit ACKs persist their update timestamp; ambiguous edit outcomes remain pending when no sufficient acknowledgment exists.

Only the exact former “Owned protective order no longer satisfies the reviewed plan” block can undergo this recovery. A read-only management pass verifies the current owned position, exact full-size live SL and maker provenance before changing status to `placing_protection`. That pass makes no financial mutation. The worker can then continue the originally reviewed target on its next round. Other blocked reasons remain blocked.

Explicit entry ACK responses include `placed_at` in UTC Unix seconds. Broker `created_at` is preferred; only a newly received ACK may fall back to its current acknowledgment time. Managed state exposes nullable `placed_at` and `entry_request_id` alongside exact `entry_order_id`. Observing an existing parent supplies its actual broker creation time; restored plans never receive a fabricated current-time placement. Adoption, closing, cancellation and protection do not create an entry placement time.

## Server-side entry evidence and anti-chasing

Every reviewed managed entry independently fetches public `/v2/history/candles` evidence before persisting its plan or changing leverage. It repeats the check concurrently with the final fresh position/order/quote preflight before the entry POST. The reviewed source must be the latest closed UTC-aligned candle for its supported interval, backed by at least fifteen contiguous closed bars. Missing/stale evidence, directional entry gaps above half an ATR, an unusually sharp final closed candle (range above two ATR or body above 1.5 ATR), and an unconfirmed crossing of a confirmed pivot reject the entry for another review. Forming candles never authorize entry. This check applies only to new entries; it does not alter protection for existing positions or adoption.

A new explicit current-position adoption may supersede prior **blocked** plans for the same owner/account/symbol after all fresh position/fill-marker and current-order checks pass. Superseding those blocked records and inserting the reviewed replacement plan occur in one SQLite transaction under the shared account/product lock. Their terminal status becomes `rejected` with “Superseded by reviewed current-position protection.” Active, pending, closing or other nonterminal plans still prevent readoption. Registration itself never changes broker orders.


## Filled-entry observation lag

A fully filled parent followed by a zero real-time position does not by itself finish a plan: the position endpoint can lag the fill acknowledgment. Management forces a fresh complete fill read and requires a coherent original-parent entry-to-flat lifecycle before any filled entry is marked terminal. Every increase must belong to the reviewed parent; normal or liquidation reductions must form an unbroken signed-size chain back to zero with exact fill UUID snapshots. Missing/inconsistent evidence keeps the worker waiting, so its next observation can place the original reviewed SL when the filled position appears. A resting parent remainder is still cancelled first if a partial position becomes flat.

Only historical `completed` plans with the former exact flat-completion message, no previously observed position/entry price, and no SL/target/close children qualify for lag recovery. The recovery pass requires the owned parent fully filled and a current complete original-parent-only position lifecycle. It performs no financial mutation: it records the verified exposure and returns to `placing_protection`; a subsequent worker tick can submit the original reviewed SL. Foreign/reopened exposure does not inherit protection. A proven already-closed lifecycle stays terminal and is excluded from further recovery rounds.

The server also rejects a directional reviewed entry price more than one ATR behind the latest closed candle, mirroring the UI's stale deep-pullback bound; the existing half-ATR chase bound remains. Neither bound changes existing positions or their reviewed protection.


## Existing managed maker-stop migration

The user's explicit market-exit policy authorizes migration of already acknowledged managed maker SLs. A durable per-plan migration record binds the exact old order ID/version and current stop price. One sync places a full-size owned market stop using a deterministic child UUID while retaining the old stop. A later sync observes the correct market type, mark trigger, reduce-only side and full quantity before cancelling only the unchanged old stop; no cancel is combined with placement. More parent fills resize the new market stop first. Unknown placement outcomes block cancellation and retries. Rejected or altered replacement evidence, changed old orders or uncertain ownership leave the old stop intact and pause management. Manual close can still close verified exposure; flat cleanup includes both owned migration siblings. Foreign stops require the existing explicit adoption review.

Sizing now reports nullable `taker_fee_rate` from the product's fractional `taker_commission_rate`; entry allocation still budgets maker entry fees and GST. Accounting's `estimated_exit_fee` uses the taker rate plus GST and `exit_fee_basis: taker`. Net P&L subtracts that market-exit estimate. `estimated_maker_exit_fee` remains a genuine separate maker estimate for compatibility and must not substitute for missing taker data. Missing taker metadata leaves market-exit estimate and net P&L null. Flat-position current costs remain zero.

Automatic `trail` decisions additionally enforce a server-side fee-covering floor from fresh verified actual entry costs plus the current estimated taker exit cost, divided by the current coin quantity. Long stops must exceed entry by those costs plus at least one full tick; shorts mirror the condition. The browser targets a nominal two-tick buffer rounded toward entry, which still retains that one-tick minimum. This prevents older maker-fee browser logic from submitting a loss-making automatic trail. Existing tightening, tick alignment, current mark and liquidation checks remain. Explicit manual SL edits retain their separate reviewed behavior.
